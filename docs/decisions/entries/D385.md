## D385: `main` takes the full ruleset: pull request, resolved threads, `check` and `browser gate`

- Status: amends D175; replaces the interim ruleset of D384
- Date: 2026-11-09 (the owner chose the append-only start in D384; this is the step it named)
- Decision: `.github/rulesets/main.json` holds no deletion, no force push, linear history, a pull request with its review threads resolved and squash as the only merge method, and the required checks `check` and `browser gate`. No approval count (one owner cannot approve their own PR; code review is CodeRabbit, D143, D192), no bypass actor, and the branch must be up to date with `main` at merge (the owner, on a decision card, 2026-11-09: "Yes, as D175 decided").
- Why: D300 step 5 (#776) stopped the engine committing `state/` to git, so no workflow pushes to `main` and a pull-request rule no longer fails an engine commit. `browser gate` (`ci.yml`) always runs and reports one name, so a ruleset can require the browser suites without hanging a docs PR.
- Consequences: a direct push to `main` is refused, including `docs: deploy now [deploy]`; a deploy goes through a PR whose squash title ends `[deploy]` (D375). A red `check` or `browser gate` blocks the merge. Because the branch must be up to date, a PR behind `main` cannot merge until it is updated and its checks rerun (about 4 minutes, 15 with the browser suites), and `automerge.yml` prints a notice and leaves a behind PR for a hand merge.
- Revisit if: a workflow must push to `main` again (add a bypass the platform accepts, or move the push to a PR), or the rerun wait after every other merge costs more than the broken-`main` risk it removes (set `strict_required_status_checks_policy` to false in the JSON and the ruleset).
