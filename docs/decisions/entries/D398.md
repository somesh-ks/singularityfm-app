## D398: singularityfm.app is a landing page; the player moves to play.singularityfm.app

- Status: active
- Date: 2026-11-23
- Decision: the player answers at `play.singularityfm.app` (`url` in `site.json`) and `singularityfm.app` (`home`) shows a static landing page (owner, 23 Nov). One Vercel project serves both hosts. `index.astro` rewrites `/` on the home host to `about.astro`, which draws no app shell, player, scripts or service worker. A host-conditioned redirect in `apps/web/vercel.json` sends every other path on the home host to the same path on the player's host. It leaves `/_astro/` (the landing page's styles and fonts), `/api/` (cron calls do not follow redirects), `/favicon.svg` and `/sw.js` alone. `sw.js` stays so a worker installed on the home host during D397's hour can still update. The redirect is temporary (307) until the move is verified. The admin proxies `/api/health` and `/api/costs` to the player's host. Amends D397.
- Why: a front door that says what Singularity is, apart from the installable player.
- Consequences: per-origin state (favorites, queue, the installed app, push subscriptions) starts empty again on the player's host. Simple Analytics counts the player's host. Old `news.someshks.*` hosts redirect to the player's host.
- Revisit if: the landing page needs content from the store, or its own deploy cadence, which would argue for a separate project.
