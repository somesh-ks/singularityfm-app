# Delivery failures

Why pull requests, CI, builds and deployments failed from 2026-10-15 to 2026-11-13, and the rule that stops each one coming back. Written 2026-10-22 after the owner asked for it; rows since then are added as they happen. Evidence is the run or deployment named; "inferred" marks what no log states. Add a row when a new kind of failure appears; do not repeat one that is here.

## The rules

1. **One push per PR, after the checks pass locally.** `npm run gate -- --build`, both browser suites for site changes, and Biome on the touched files in a worktree (`npm run lint` checks nothing there). Every push to an open PR cancels the last CI run and starts a new one, and both are billed (classes 1, 4, 5).
2. **A preview deploys only from a branch named `preview/*`, in every Vercel project.** Any other branch, the agents' included, gets no Vercel preview and no Neon branch (classes 2, 15). A new project's `vercel.json` carries `git.deploymentEnabled` and an `ignoreCommand` from day one; `vercelJson.test.ts` fails without them.
3. **Merge `main` into an open branch after `main` changes `apps/web/vercel.json` or a workflow.** Vercel and Actions read those files from the branch's own commit, so an old branch keeps the old rules (class 2).
4. **A red check is classified before anyone acts on it:** billing, Vercel branch limit, a cancelled run, an ignored build, a known flake, or a real failure. Only the last needs a code change (classes 1 to 6).
5. **Never remove a worktree or branch another session made.** A worktree with no commits looks merged and is someone's work in progress (class 8).
6. **Verify branch HEAD after pushing.** After `git push`, compare `git ls-remote origin <branch>` with `git rev-parse HEAD`. A push on a detached HEAD reports "Everything up-to-date" while remote remains stale (class 11).
7. **Workers never allocate decision IDs.** Decision numbers are assigned strictly by the lead on `main` right before merge to avoid parallel branch collisions (class 12).
8. **The owner's config is not in git (D296).** Edit it in the app or the store, never in a pull request: the files under `config/` named in `CONFIG_DOCUMENT_PATHS` are ignored, and `config/examples/` holds only public defaults (class 13).
9. **A PR that GitHub shows as conflicting is also an unchecked one.** Fetch `main` and merge it as soon as `mergeable_state` reads `dirty`, then read the first `ci` run on the merged head before calling the branch green (class 14).
10. **Probe what a build depends on before paying for it.** A scheduled or hook build that reads the content store asks the store first and does nothing on a refusal (`deploy-due.yml`, #804). Retrying a refusal never fixes it (class 16).
11. **Moving a repository moves its Vercel project settings too, and they are not in git.** After repointing a project, clear or fix its Root Directory and build once from the new repository before the old folder is deleted (class 18).
12. **A red browser shard is read by cause before it is run again.** The job page names it: `code` (fix it; running again hides a regression), `infra` (the shard already reran once), `flaky` (a name to fix if it repeats) or `unknown` (read the log). Only the install steps and an `infra` shard (once) run again on their own (class 22, D393).

## The merge flow, as designed (not failures)

Every PR carries `review`, so it merges after the review lands, by its thread (D143; `code-review.md`, Who merges); `automerge` merges Dependabot only, and its token cannot merge a PR that edits `.github/workflows`. `browser` (`browser.yml`: two player and three site shards) runs for any PR that changes `apps/web`, `packages`, the tokens, the build scripts or the lockfile, on every push to `main` except docs, digest and state commits, and nightly at 02:17 UTC (2026-10-26; it was path-gated before and #346 skipped it).
